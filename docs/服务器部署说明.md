# 服务器部署说明（受限环境）

适用场景：一台**什么都没装**的服务器，**根目录不可写**，只有 `/mnt` 可写，已装好 conda。
从新建 conda 环境开始，一路到跑出训练数据。

全文假设可写目录是 `/mnt`。如果你的可写路径不同，把下面所有 `/mnt/fv` 换掉即可。

> **可写 ≠ 持久。** 本项目踩过：`/mnt/fv` 每次重启都被清空，MySQL 的 datadir 放在
> 那里，一次重启丢了 2524 万行账本。**凡是重装都能再来一遍的东西**（conda 环境、
> 包缓存、临时目录）放哪都行；**丢了就回不来的东西**（MySQL datadir、产出的 JSONL
> 和图片）必须放在确认持久的卷上。怎么确认见第 9 步。

---

## 第 0 步：先搞清楚三件事

在动手之前确认这三点，能省掉后面 90% 的坑：

```bash
# 1. 哪些目录能写？
touch /mnt/.writetest && echo "/mnt 可写" && rm /mnt/.writetest
touch ~/.writetest 2>/dev/null && echo "HOME 可写" && rm ~/.writetest || echo "HOME 不可写 —— 必须做第 2 步的重定向"
touch /tmp/.writetest 2>/dev/null && echo "/tmp 可写" && rm /tmp/.writetest || echo "/tmp 不可写 —— 必须设 TMPDIR"

# 2. /mnt 还有多少空间？（下面第 7 步会算你到底需要多少）
df -h /mnt

# 3. 能不能连外网装包？
curl -sS -m 10 https://pypi.org/simple/ -o /dev/null && echo "外网通，走在线安装" || echo "外网不通，走离线安装"
```

**HOME 不可写是最容易翻车的一点**：conda 和 pip 默认都往 `$HOME` 里写缓存和配置，不重定向的话第一条命令就报 `Permission denied`。

---

## 第 1 步：建目录结构

```bash
mkdir -p /mnt/fv/{envs,pkgs,pipcache,tmp,code,data/zips,output}
```

| 目录 | 用途 |
| --- | --- |
| `/mnt/fv/envs` | conda 环境 |
| `/mnt/fv/pkgs` | conda 包缓存 |
| `/mnt/fv/pipcache` | pip 缓存 |
| `/mnt/fv/tmp` | **临时目录，解压 zip 用，需要很大**，见第 7 步 |
| `/mnt/fv/code` | 代码 |
| `/mnt/fv/data/zips` | 你的数据集 zip |
| `/mnt/fv/output` | 产出的训练数据和图片 |

---

## 第 2 步：把所有默认写入路径重定向到 /mnt

建一个环境文件，**以后每次登录、每个脚本都先 source 它**：

```bash
cat > /mnt/fv/env.sh <<'EOF'
# conda：环境和包缓存都不放 HOME
export CONDA_ENVS_DIRS=/mnt/fv/envs
export CONDA_PKGS_DIRS=/mnt/fv/pkgs

# pip：缓存不放 HOME
export PIP_CACHE_DIR=/mnt/fv/pipcache

# 临时目录：解压 zip 会往这里写几十 GB，绝不能用默认的 /tmp
export TMPDIR=/mnt/fv/tmp

# MySQL 密码（用到 db 模式时才需要，别写进 git）
export FV_MYSQL_PASSWORD='改成你的密码'
EOF

source /mnt/fv/env.sh
```

`TMPDIR` 只有 **zip 形式**的数据集才用得到（解压落地用），目录形式全程不写临时文件。设上没坏处，pip 装包时也要用。原因见第 7 步。

如果做完这些还有东西往 HOME 里写导致报错，最后的兜底是连 `HOME` 一起改：

```bash
export HOME=/mnt/fv/home && mkdir -p "$HOME"
```

---

## 第 3 步：建 conda 环境

项目要求 **Python ≥ 3.11**。

```bash
source /mnt/fv/env.sh
conda create -p /mnt/fv/envs/fv python=3.11 -y
conda activate /mnt/fv/envs/fv
python -V   # 应该显示 3.11.x
```

注意用 `-p`（指定完整路径）而不是 `-n`（放进 conda 自带的 envs 目录）。如果 conda 装在不可写的位置，`-n` 会失败。

## 第 4 步：装包

### 运行时只需要 4 个包

```bash
pip install "httpx>=0.27,<1" "pyarrow>=15,<22" "tqdm>=4,<5" "PyMySQL>=1.1,<2"
```

说明：

- `requirements.txt` 里还有 `Pillow` 和 `pytest`。**这两个跑起来用不到**：`pytest` 只在跑测试时要；`Pillow` 源码里根本没 import（处理 PIL 图片走的是鸭子类型判断），装了纯属浪费带宽。要跑测试再补 `pip install pytest`。
- `PyMySQL` 只有用 MySQL 模式才需要。纯文件模式可以不装。
- 最大的包是 `pyarrow`（约 40 MB wheel，装完约 200 MB）。

### 外网不通就走离线

在一台**能上网、同架构（Linux x86_64）、同 Python 版本**的机器上先下好：

```bash
pip download --only-binary=:all: --platform manylinux2014_x86_64 \
  --python-version 311 --implementation cp -d ./wheels \
  "httpx>=0.27,<1" "pyarrow>=15,<22" "tqdm>=4,<5" "PyMySQL>=1.1,<2"
tar czf wheels.tar.gz wheels
```

拷到服务器后：

```bash
tar xzf wheels.tar.gz -C /mnt/fv/
pip install --no-index --find-links=/mnt/fv/wheels \
  httpx pyarrow tqdm PyMySQL
```

## 第 6 步：放数据和改配置

### 数据

数据有两种组织形式，**按你实际的目录结构选一种**。

#### A. 目录形式（FineVision 风格，推荐）

数据长这样，一个数据集一个文件夹，里面是裸 parquet：

```text
/mnt/.../FineVision/
├── README.md
├── CoSyn_400k_chart/
│   ├── train-00000-of-00052.parquet
│   └── ... 共 52 个
├── arxivqa/
└── ... 几百个目录
```

几百个目录不用一个个写，开自动发现就行：

```bash
cat > configs/datasets.json <<'EOF'
{
  "data_root": "/mnt/si003010kcx0/mmdata/mm_general/FineVision",
  "auto_discover": true
}
EOF
```

> **别手敲这个路径。** 挂载点名字里的 `0`(零)/`O`(大写o)、`1`(一)/`l`(小写L) 在终端等宽字体里几乎无法分辨，抄错一个字符就是 `data_root does not exist`。让 shell 自己填：
>
> ```bash
> cd /mnt/si003010kcx0/mmdata/mm_general/FineVision   # 能 cd 进去就说明路径对
> DATA_ROOT="$PWD"
> cd -   # 回到项目目录
> python -c "import json,os;json.dump({'data_root':os.environ['DATA_ROOT'],'auto_discover':True},open('configs/datasets.json','w'),indent=2)"
> cat configs/datasets.json
> ```
>
> 用 Tab 补全 `cd` 进去，再拿 `$PWD` 回填，一个字符都不会错。

`auto_discover` 会把 `data_root` 下**每个含有 parquet 的子目录**注册成一个数据集，目录名即数据集名。根目录的 `README.md` 这类散文件会被忽略。

想挑着来：

```json
{
  "data_root": "/mnt/.../FineVision",
  "auto_discover": { "include": ["CoSyn_400k_chart", "arxivqa", "chartqa"] }
}
```

或者排除几个：

```json
{
  "data_root": "/mnt/.../FineVision",
  "auto_discover": { "exclude": ["docvqa", "unigeo(mathv360k)"] }
}
```

确认发现了哪些（**这一步别跳过**）：

```bash
PYTHONPATH=src python -m finevision_to_sharegpt list-datasets \
  --config configs/export_zips.json --limit 10
```

核对末尾的 `total`。预期几百个却只有 1 个，就是 `data_root` 指高了一层，父目录被整个当成了一个数据集，往下再指一级。

**目录形式不需要解压**，parquet 就地读取，所以完全不占 `TMPDIR`，启动也快。

#### B. zip 形式

数据是一个个 zip 包时，逐个登记：

```bash
cat > configs/datasets.json <<'EOF'
{
  "data_root": "/mnt/fv/data/zips",
  "datasets": {
    "okvqa":   { "zip": "okvqa.zip" },
    "chartqa": { "zip": "chartqa.zip" }
  }
}
EOF
```

两种可以混着用，`dir` 和 `zip` 在同一个注册表里各写各的。

### 批量注册（可选，把发现结果固化）

`auto_discover` 每次运行都重新扫。想固化成显式清单（锁定范围、可手工删减）：

```bash
python scripts/register_datasets.py /mnt/si003010kcx0/mmdata/mm_general/FineVision --dry-run
python scripts/register_datasets.py /mnt/si003010kcx0/mmdata/mm_general/FineVision -o configs/datasets.json
```

### 模型后端

```bash
cat > configs/backend_config.json <<'EOF'
{
  "request_timeout": 120,
  "max_retries": 2,
  "disable_backend_after_failures": 20,
  "backends": [
    { "name": "gpu0", "api_base": "http://10.0.0.1:18180/v1/chat/completions",
      "model": "Qwen3-VL", "api_key": "sk-local", "concurrency": 16, "weight": 1 },
    { "name": "gpu1", "api_base": "http://10.0.0.2:18180/v1/chat/completions",
      "model": "Qwen3-VL", "api_key": "sk-local", "concurrency": 24, "weight": 1 }
  ]
}
EOF
```

多卡多模型就多写几个 backend，`concurrency` 是每个 backend 的固定并发。

`api_base` 必须是**完整的** `/v1/chat/completions` 地址。模型清单上给的 Base URL 通常只到 `/v1`，要自己补后半截。

填好之后**先探活再开跑**：

```bash
python scripts/check_backends.py configs/backend_config.json
```

它会对每个 backend 发两次极小的请求：一次纯文本，一次带一张 1x1 图片。三件事一次查清 —— 地址通不通、key 对不对、**模型认不认图片**。

最后一条是硬要求：翻译时每条样本的图片都会以 base64 发出去，纯文本模型会在**每一条**上失败。报错里出现 `this model rejects images` 就说明用错模型了，得换视觉模型（VL）。

### 任务配置

```bash
cat > configs/translate_zips.json <<'EOF'
{
  "dataset_registry": "configs/datasets.json",
  "datasets": ["*"],
  "output_jsonl": "/mnt/fv/output/train.jsonl",
  "chinese_ratio": 1.0,
  "seed": 42,
  "limit_per_dataset": 5000,
  "backend_config": "configs/backend_config.json",
  "emit_raw": true,
  "resume": true
}
EOF
```

**输出路径写成 `/mnt` 下的绝对路径**，别用相对路径掉进不可写的地方。

## 第 7 步：算清楚磁盘和内存（重要）

**如果你的数据是目录形式（上一步的 A 方案），这一步基本可以跳过** —— parquet 就地读取，不解压、不占临时空间，只要输出目录装得下图片就行。

zip 形式则有两个硬性下限：`extract_parquets_from_zip` 处理一个数据集时，会把**这个 zip 里所有 parquet 一次性全解压**到 `TMPDIR`，而且每个成员是**整个读进内存**再写盘的（`target.write(source.read())`）。所以：

| 资源 | 下限 | 怎么估 |
| --- | --- | --- |
| `TMPDIR` 可用空间 | ≥ **单个 zip 解压后的总大小**（目录形式为 0） | 用下面的脚本 |
| 可用内存 | ≥ **该 zip 里最大的那个 parquet 成员**（目录形式无此限制） | 用下面的脚本 |
| 输出目录 | 图片总量 + JSONL | 图片按内容 hash 去重落盘，重复图只存一份 |

仓库里带了个脚本直接帮你算，还会拿 `TMPDIR` 的实际剩余空间对比给结论：

```bash
source /mnt/fv/env.sh
python scripts/estimate_space.py /mnt/fv/data/zips
```

脚本认得两种形式。目录形式的输出：

```text
CoSyn_400k_chart  [dir]
  parquet files   : 52
  on-disk size    :    31.20 GB  -> read in place, no temp space
...
datasets: 0 zip, 214 directory
all datasets are directories -> TMPDIR is not used by the pipeline
```

zip 形式的输出：

```text
okvqa.zip  [zip]
  parquet members : 12
  uncompressed    :    48.30 GB  -> needs temp space
  largest member  :     4.10 GB  -> needs memory

TMPDIR needs at least :    48.30 GB
free memory at least  :     4.10 GB
TMPDIR=/mnt/fv/tmp has 512.00 GB free -> OK
```

空间不够时会打印 `TOO SMALL` 并以非 0 退出码结束，方便串进部署脚本里做前置检查。

`TMPDIR` 空间不够的典型症状是跑到一半 `No space left on device`。内存不够则是 OOM 被杀。

多个数据集是**逐个处理**的，临时目录用完即清，所以按**最大的那一个** zip 算就够，不用把所有 zip 加起来。

## 第 9 步（可选）：接 MySQL 做增量抽取

**不配就完全用不到**，上面的流程本身是完整的。需要"用多少抽多少、跨任务不重复"时再来这一步。

### 先准备一个 MySQL

这个项目**不负责装 MySQL**，但仓库里带了个一键脚本，适合「只有某个目录可写、没有
包管理器权限、但装了 conda」的机器。

#### 先选好 datadir 放哪 —— 这一步错了会丢整个账本

脚本的第一个参数是 **BASE**，datadir、socket、pid、日志、`my.cnf` 全在它下面。
**这个目录被清空 = 账本没了**，不是缓存，是几千万行。

本项目已经因为把 BASE 放在重启即清空的卷上，丢过一次 2524 万行的账本。
所以别照抄任何路径（包括这份文档里的），**在你自己的机器上问出来**：

```bash
df -h                     # 看有哪些卷、各自多大
lsblk -o NAME,SIZE,MOUNTPOINT 2>/dev/null || true
```

判据很简单：**上次重启后还在的东西，在哪个卷上，哪个卷就是持久的。**
你的代码和已产出的数据都活过了那次重启，所以它们所在的卷就是答案：

```bash
cd <你的代码目录> && df -P . | awk 'NR==2 {print "代码在:", $1, "挂载于", $6}'
```

把 BASE 放在同一个卷上。脚本自己也会做这个比对，发现 BASE 和代码不在一个卷上时
会打印警告 —— **看到警告就停下来想一下，别直接往下走。**

> 路径一律用 `ls` / `df` 自己敲出来或用 Tab 补全，不要从聊天记录或截图里抄。
> 挂载点里的 `0/O`、`1/l` 在等宽字体下分不清，这个错误在本项目里造成过两次返工。

#### 方案一：装进你已有的 fv 环境（推荐）

你已经有一个 `fv` 环境了，把 MySQL 装进同一个环境最省心：`conda activate` 之后
`mysqld` 和 `mysql` 就直接在 PATH 上，不用记第二个路径。

```bash
conda activate <你的 fv 环境>
python -c "import sys; print(sys.prefix)"    # 确认这就是 fv 环境，下面直接用 $CONDA_PREFIX
```

```bash
export FV_MYSQL_PASSWORD='你自己定一个密码'
export FV_MYSQL_ENV="$CONDA_PREFIX"
bash scripts/setup_local_mysql.sh <持久卷>/fv-mysql
```

`FV_MYSQL_ENV` 指定**二进制装到哪**，BASE 只放**状态**，两件事分开。
用 `$CONDA_PREFIX` 而不是手写路径，就不存在抄错的可能。

脚本可重复执行（已有 datadir 会复用而不是重新初始化），做四件事：

1. 往 `$FV_MYSQL_ENV` 里 `conda install mysql-server=8.4.2 mysql-client=8.4.2`
2. 初始化 datadir 到 `<BASE>/data`
3. 启动 mysqld，socket / pid / 日志全在 `<BASE>/` 下
4. 建库建号，并打印可直接粘贴的 `mysql` 配置段

> 已存在的环境只能 `conda install`，不能 `conda create` —— 后者会拒绝碰已有前缀。
> 脚本按目录在不在自动选，不用你操心。

#### 方案二：已有内网 MySQL（有现成的就用现成的）

建库和账号就行，不用跑脚本：

```sql
CREATE DATABASE finevision CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE USER 'fv'@'%' IDENTIFIED BY '你的密码';
GRANT ALL PRIVILEGES ON finevision.* TO 'fv'@'%';
FLUSH PRIVILEGES;
```

远程库要多装一个包：`pip install cryptography`（本机连接不需要，见下）。

#### 每次重启之后要重跑

**mysqld 不会开机自启。** 服务器重启后账本连不上，多半就是这个原因。
重跑同一条命令即可，datadir 会被复用，数据不会丢（前提是 BASE 在持久卷上）：

```bash
conda activate <你的 fv 环境>
export FV_MYSQL_PASSWORD='...' FV_MYSQL_ENV="$CONDA_PREFIX"
bash scripts/setup_local_mysql.sh <持久卷>/fv-mysql
```

已经在跑的话脚本会说 `== already running`，不会重复启动。

停止：

```bash
kill $(cat <持久卷>/fv-mysql/mysqld.pid)
```

#### 三个实测踩过的坑，脚本里都已经处理

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| mysqld 读到系统 `/etc/my.cnf` | `unknown variable 'expire_logs_days'`，初始化直接失败 | 自带 `my.cnf` 并用 `--defaults-file` 独占加载 |
| conda 的 `mysql-server` 不含客户端 | `mysql: No such file or directory` | 同时装 `mysql-client` |
| MySQL 拒绝以 root 身份运行 | `Please read "Security" section ... run mysqld as root!` | 配置里写入 `user = $(id -un)` |

环境变量可覆盖：`FV_MYSQL_PORT`（默认 3306）、`FV_MYSQL_DATABASE`、`FV_MYSQL_USER`、`FV_MYSQL_ENV`。

#### 不用去调 max_connections

脚本写死 `max_connections = 256`，够用，**别按并发数去估**。
连接池是有界共享的，几百路翻译并发在服务端也只占 `mysql.pool_size` 条（默认 8）。

`SET GLOBAL max_connections = ...` 也没有意义 —— 脚本每次运行都会重写 `my.cnf`，
重启后就恢复了。真要改，改 `mysql.pool_size`，那才是实际占用数。

#### 版本说明

选 **8.4.2**，是 LTS 线。conda-forge 上还有 8.0.33 和 9.x，9.x 是激进版本线，生产不建议。

`PyMySQL` 单独就够 —— MySQL 8.4 默认的 `caching_sha2_password` 认证，实测在冷缓存下
也能连上，不需要额外装 `cryptography`。只有当服务端强制 TLS 或在远程主机上时才需要补它。

### 配置

在任务配置里加一段 `mysql`：

```json
{
  "mysql": {
    "host": "127.0.0.1",
    "port": 3306,
    "user": "fv",
    "password": "${FV_MYSQL_PASSWORD}",
    "database": "finevision",
    "batch_size": 200,
    "pool_size": 8,
    "claim_ttl_seconds": 3600,
    "on_connect_error": "fail"
  }
}
```

密码走 `${FV_MYSQL_PASSWORD}` 环境变量（已经在 `env.sh` 里设好了），不要写死进文件。

`on_connect_error` 两个取值差别很大：`"fallback"` 连不上就退回纯文件模式继续跑，
**不报错**，等你发现时已经产出了一批不受账本管的数据；`"fail"` 直接失败。
既然是靠账本去重的，用 `"fail"`。

### 建表

库和账号有了之后建表，幂等，可以反复跑：

```bash
python -m finevision_to_sharegpt db-init --config <你的配置>
python -m finevision_to_sharegpt db-status --config <你的配置>
```

`db-init` 会建 4 张表加每个数据集一个视图。`db-status` 返回空统计就说明连通了。

### 账本丢了但产出还在：db-restore

账本和产出在两个卷上时，可能账本整个没了而 JSONL 完好。此时**别直接续跑** ——
空库的 `resume` 一条都跳不过去，已翻的会重做一遍，还会往同一个 JSONL 里追加重复记录。

先灌回去：

```bash
python -m finevision_to_sharegpt db-restore --config <你的配置> --dry-run
python -m finevision_to_sharegpt db-restore --config <你的配置>
```

`--dry-run` 先看数对不对（`source_rows` / `translations` 应该和你产出的条数吻合），
再去掉它真写。产出目录不在配置的 `output_jsonl` 上级时，用 `--output-dir` 指过去。

它会同时重建 `sample_source`、`sample_translation` 和 `dataset_cursor`。
**三者缺一不可** —— 只补 `done` 行而不重建水位线，`is_consumed` 对水位线之上的行
一律返回未消费，恢复等于没做。

### 建表并使用

```bash
bash scripts/in_db_init.sh configs/translate_zips.json    # 建表，幂等
bash scripts/in_translate_zips.sh                          # 抽 5000 条
bash scripts/in_translate_zips.sh                          # 再抽 5000 条全新的
bash scripts/in_db_status.sh configs/translate_zips.json   # 看各状态计数
```

`limit_per_dataset` 是**本次新增 N 条**的意思，所以重复运行就是不断往下抽新数据，两次的输出目录不同也不会重复。

## 常见问题

| 症状 | 原因 | 解决 |
| --- | --- | --- |
| `Permission denied` 在装包时 | conda/pip 往 HOME 写 | 第 2 步的 `CONDA_PKGS_DIRS` / `PIP_CACHE_DIR` |
| `No space left on device` 跑到一半 | zip 形式下 `TMPDIR` 太小 | 第 2 步设 `TMPDIR=/mnt/fv/tmp`，并按第 7 步核对空间；或改用目录形式 |
| 进程被 OOM kill | zip 形式下单个 parquet 成员太大 | 见第 7 步；目录形式没有这个问题 |
| `dataset 'x' must include zip or dir` | 注册表条目写错 | 每个数据集要么 `{"dir": "..."}` 要么 `{"zip": "..."}` |
| `auto_discover: data_root ... does not exist` | 路径拼错 | 报错会指出断在哪一层、那层里实际有什么，照着改 |
| `auto_discover found no datasets` | `data_root` 层级不对 | 报错会列出子目录；parquet 在更深一层就往下指 |
| `list-datasets` 只显示 1 个数据集 | `data_root` 指高了一层 | 父目录被当成单个数据集，往下再指一级 |
| 自动发现少了某些数据集 | 那些目录里没有 `.parquet` | 只有含 parquet 的子目录会被注册 |
| `No module named finevision_to_sharegpt` | 没设 PYTHONPATH | 用 `scripts/in_*.sh`，它会自己设；或手动 `export PYTHONPATH=src` |
| `environment variable FV_MYSQL_PASSWORD ... is not set` | 没 source `env.sh` | `source /mnt/fv/env.sh` |
| 翻译全部 failed | 模型接口不通 | `curl` 试一下 `api_base`；看 `failed.jsonl` 里的 error |
| MySQL 连不上但任务照跑 | `on_connect_error: "fallback"` 的预期行为 | 想让它直接报错就改成 `"fail"` |
| 建表报 collation 不存在 | 服务端不是 MySQL 8.x（如 MariaDB） | 在 `mysql` 段加 `"collation": "utf8mb4_general_ci"` |
| mysqld 起不来，报 unknown variable | 读到了系统 `/etc/my.cnf` | 用 `setup_local_mysql.sh`，它以 `--defaults-file` 独占加载自带配置 |
| `Please read "Security" section` | 以 root 运行 mysqld | 配置里加 `user = root`；脚本已自动处理 |
