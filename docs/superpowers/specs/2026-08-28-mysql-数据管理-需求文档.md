# finevision-to-sharegpt MySQL 数据管理需求文档

状态：需求阶段，未实现任何代码。本文档用于对齐范围和拍板未决项。

## 一、目标

在**完全不破坏现有纯文件流水线**的前提下，接入 MySQL 做「数据资产 + 消费账本」管理，达成三件事：

1. **增量抽取**：用多少抽多少，跨任务、跨输出目录都不重复抽到同一条样本。
2. **源数据与翻译分离存储、可关联查询**：源数据一张大表，翻译一张表，通过 `sample_id` 关联。
3. **数据集换版可感知**：zip 换一版后，历史消费记录自动隔离，不会静默失效。

## 二、现状与缺口

现有增量能力已部分存在，但受限于文件式状态：

| 现状 | 位置 | 缺口 |
| --- | --- | --- |
| `dataset_stats` 每次运行新建，已消费样本走 `skipped` 不计入 `written` | `zip_pipeline.py:209`、`zip_pipeline.py:222` | `limit` 语义是「本次新增 N」而非「累计上限 N」，需确认是否符合预期 |
| `completed_ids` 只从本次 `output_jsonl` 加载 | `zip_pipeline.py:192` | 换输出目录跑第二批会从 row 0 重抽，两批数据重叠 |
| 跳过靠逐行比对 `sample_id` | `zip_pipeline.py:222` | 抽到第 100 万行后，再要 5000 条得先解压 zip 空转 100 万行 |
| `completed_ids` 全量进内存 | `zip_pipeline.py:192` | 百万级 `set[str]` 占用数百 MB |
| `sample_id = zipstem:parquet:row_index` | `zip_pipeline.py:221` | 不抗数据集换版 |

## 三、硬约束

### 3.1 双模式，file 模式为默认

- **file 模式**（默认，行为与现状逐字节一致）：零 DB 依赖。现有 `translate-json` / `translate-zips` / `export-zips` / `merge` / `validate` 全部照旧。
- **db 模式**（新增，opt-in）：任务配置中出现 `mysql` 段才启用。

**验收红线**：在没有 MySQL 的环境下，`pytest -q` 现有全部用例必须全绿，且现有三条流水线的输出与改造前完全一致。

### 3.2 不删除任何现有功能

MySQL 是**叠加**能力，不是替换。所有现有 CLI 命令、配置字段、输出文件结构保持不变。

### 3.3 连不上数据库的行为可配置

`on_connect_error` 两种取值：
- `fallback`：打印告警，降级为 file 模式继续跑完（推荐默认）。
- `fail`：立即退出，避免"以为在记账其实没记"。

## 四、数据模型

### 4.1 分层

用户表述："源数据放大一个大表，按照数据集划分小表，翻译放到一个，然后跟源数据逻辑一下"。落成四张表：

```
dataset_version   ── 数据集版本表（zip 指纹，解决换版问题）
      │
      ├─< sample_source      ── 源数据大表（英文原文 + 消费状态）
      │         │
      │         └─< sample_translation  ── 翻译表（中文译文，关联 source_id）
      │
      └─< dataset_cursor     ── 扫描水位线（性能优化）
```

### 4.2 dataset_version（数据集版本表）

```sql
id            BIGINT UNSIGNED PK AUTO_INCREMENT
dataset       VARCHAR(128)   NOT NULL
source_file   VARCHAR(512)   NOT NULL   -- zip 相对路径
source_hash   CHAR(64)       NOT NULL   -- zip 指纹
file_size     BIGINT         NOT NULL
file_mtime    BIGINT         NOT NULL
images_root   VARCHAR(512)              -- 该版本图片落盘根目录
first_seen_at DATETIME       NOT NULL
UNIQUE KEY uk_ds_hash (dataset, source_hash)
```

换版 = 新 `source_hash` = 新一行。历史消费记录挂在旧 `version_id` 上，天然隔离，不会误判为"已抽过"。

### 4.3 sample_source（源数据大表）

```sql
id               BIGINT UNSIGNED PK AUTO_INCREMENT
version_id       BIGINT UNSIGNED NOT NULL   -- → dataset_version.id
dataset          VARCHAR(128)    NOT NULL   -- 冗余列，便于按集查询/建索引
sample_id        VARCHAR(512)    NOT NULL   -- zipstem:parquet:row_index
parquet_name     VARCHAR(255)    NOT NULL
row_index        INT             NOT NULL
conversations    JSON            NOT NULL   -- 英文原文 ShareGPT conversations
image_paths      JSON                       -- ["images/okvqa/ab12.jpg", ...] 只存路径
image_count      SMALLINT        NOT NULL DEFAULT 0
status           ENUM('pending','claimed','done','failed','rejected') NOT NULL
lang_assigned    ENUM('zh','en')            -- hash 分流结果
reject_reason    VARCHAR(255)
batch_id         VARCHAR(64)
claimed_at       DATETIME
claim_expires_at DATETIME
done_at          DATETIME
UNIQUE KEY uk_ver_sample (version_id, sample_id)
KEY idx_pick   (dataset, status, id)
KEY idx_batch  (batch_id)
KEY idx_expire (status, claim_expires_at)
```

### 4.4 sample_translation（翻译表）

```sql
id             BIGINT UNSIGNED PK AUTO_INCREMENT
source_id      BIGINT UNSIGNED NOT NULL   -- → sample_source.id（关联点）
version_id     BIGINT UNSIGNED NOT NULL
sample_id      VARCHAR(512)    NOT NULL   -- 冗余，便于不 join 直接查
conversations  JSON            NOT NULL   -- 中文译文
backend_name   VARCHAR(64)                -- 哪个 backend 翻的
model_name     VARCHAR(128)               -- 哪个模型翻的（模型池多模型可追溯）
prompt_version VARCHAR(64)                -- 提示词文件指纹
batch_id       VARCHAR(64)
latency_ms     INT
created_at     DATETIME        NOT NULL
KEY idx_source (source_id)
KEY idx_batch  (batch_id)
-- 唯一键取决于「一条源数据允许几条译文」的决策，见待定项 3
```

`backend_name` / `model_name` 落库后，可以直接查"哪个模型翻的质量差"并按模型重翻，这是模型池多 backend 场景下的实际价值。

### 4.5 dataset_cursor（扫描水位线）

```sql
version_id            BIGINT UNSIGNED NOT NULL
parquet_name          VARCHAR(255)    NOT NULL
max_scanned_row_index INT             NOT NULL
fully_scanned         TINYINT(1)      NOT NULL DEFAULT 0
updated_at            DATETIME        NOT NULL
PRIMARY KEY (version_id, parquet_name)
```

解决"再抽 5000 条要先空转 100 万行"。配合 pyarrow 按 row group 跳读，能跳过大部分解码开销。

### 4.6 图片不入库

图片**不进 MySQL**，仍按 `images/<dataset>/<hash>.<ext>` 落盘，表里只存相对路径。

理由：BLOB 会撑爆库、拖慢备份与主从复制，而 LLaMA-Factory 训练时本来就按文件路径读图。`dataset_version.images_root` 记录该版本图片的落盘根目录，避免路径与实际目录失联。

## 五、两阶段消费（claim → done）

翻译是异步的：`chinese_tasks()` 产出任务后，结果要等 `backend_pool.map_unordered` 回来才写记录（`zip_pipeline.py:163`）。若在"抽出"时就标记已消费，进程中途挂掉这批样本将**永久丢失**，再也抽不到。

流程：

1. **扫描/抽取**：`INSERT ... ON DUPLICATE KEY UPDATE` 写入 `sample_source`，`status='claimed'`，`claim_expires_at = NOW() + claim_ttl`。
2. **英文样本**：不调模型，直接写记录 → `status='done'`。
3. **中文样本**：进翻译队列 → 结果回来写 `sample_translation` + `status='done'`。
4. **翻译失败**：`status='failed'`，错误信息落 `failed.jsonl`（保持现有行为）。
5. **解析拒绝**：`status='rejected'` + `reject_reason`。
6. **崩溃回收**：下次运行时，`status='claimed'` 且 `claim_expires_at < NOW()` 的行自动回收为 `pending`，重新参与抽取。

这样"抽出但没落盘"的样本不会永久丢失。

## 六、并发写入

- **每工作线程一个连接**（`threading.local` 持有，或简易连接池），不共享连接。
- **攒批 flush**：默认 200 条或 5 秒，先到先触发。
- 使用 `executemany` + `INSERT ... ON DUPLICATE KEY UPDATE`。
- **退出前强制 flush**，包含异常路径（`try/finally`），避免最后一批丢失。
- **断线重连**：内网 MySQL `wait_timeout` 断连是常态，写入需带重连重试。
- 驱动选 **PyMySQL**（纯 Python，无编译依赖），不用 `mysqlclient`，以免破坏离线镜像构建。

## 九、验收标准

1. 无 MySQL 环境下 `pytest -q` 全绿，现有三条流水线输出与改造前一致。
2. 同一 zip 连续两次 `limit=100` 的 db 模式运行，产出 200 条互不重复。
3. 换一个不同 hash 的 zip，同名数据集重新从 0 计数，旧版本记录不受影响。
4. 翻译中途 `kill -9`，重启后过期 `claimed` 样本被回收重抽，无永久丢失。
5. `db-export` 导出结果能通过现有 `validate` 命令。
6. 单机 32 并发下 DB 写入不成为瓶颈，吞吐相比 file 模式下降小于 10%。

## 十、待拍板事项

| # | 事项 | 选项 | 建议 |
| --- | --- | --- | --- |
| 1 | 「按数据集划分小表」怎么落 | A 单大表 + `dataset` 索引，小表用 VIEW／B 物理分表 `sample_source_okvqa`／C MySQL 原生 `PARTITION BY KEY(dataset)` | **A**。无动态 DDL，跨集查询简单，加数据集零成本。B 需动态建表且跨集查询要 UNION，复杂度显著上升；C 的分区键必须进主键，加数据集要 ALTER |
| 2 | zip 指纹算法 | 全文件 sha256／`size+mtime`／头尾采样 hash + size | **头尾采样 hash + size**。全量 sha256 对几十 GB 的 zip 要整读一遍；`mtime` 在拷贝/解压后不可靠 |
| 3 | 一条源数据允许几条译文 | 单条覆盖（`UNIQUE(source_id)`）／多版本保留（`UNIQUE(source_id, model_name, prompt_version)`） | **多版本保留**更有价值（换模型重翻可对比），但导出时需定"取哪条"规则（建议取最新） |
| 4 | 源数据入库时机 | 独立 `db-scan` 一次性灌库，抽取时只读／抽取时顺便写 | 取决于你是否想先把全量源数据沉淀成资产。前者更清晰，后者省一遍扫描 |
| 5 | MySQL 环境 | 你自有实例／我在 `docker-compose.yml` 里带一个；版本 5.7 还是 8.0 | **8.0**。5.7 的 JSON 函数和 `utf8mb4` 排序规则行为有差异 |
| 6 | `limit` 语义（上一轮遗留） | 「本次新增 N」（现状）／「累计上限 N」 | 需明确，两者在 db 模式下实现方式不同 |
